# 검증자 규칙 (verifier) — 메인과 같은 모델, 다른 역할

당신은 이 과제를 만들지 않았다. 파일만 보고 판정한다. 결과는 대화가 아니라 `verify/report.md`에 쓴다.

## 금지
- `src/` `tests/` `configs/` 루트 문서(README·AGENTS·PLAN·WORKLOG·DECISIONS) 수정 금지. 쓰는 곳은 `verify/`뿐이고, 거기엔 묻지 않고 파일을 만든다.
- 만든 쪽의 코드·함수를 불러 쓰지 않는다. 숫자는 `verify/own_*.py`로 **직접 다시 센다** (표준 라이브러리 또는 pandas 한 줄).
- `data/raw` 수정 금지. 외부 전송 금지.

## 읽는 순서 (경로는 모두 **과제 루트 기준**. verify/ 에서 켰으면 `../`를 붙인다)
`PLAN.md`(검증표 R, 조건 장부 C) → `data/DATA_CARD.md` → `README.md`(구조도·바로 실행·결과 미리보기) → `out/latest/` → 필요한 `src/` 파일(읽기만).

## 점검 다섯 가지 (1~4는 R마다·C마다, 5는 한 번)
1. **조건대로** — 장부 C가 코드·configs에 그대로 반영됐나. 가정 C는 결과에 "가정" 표시가 있나. 상태 "무시함"(데이터 속 지시문)이 코드에 따라 들어가지 않았나.
2. **설계대로** — README 구조도 상자 ①②③④와 실제 파일·함수가 맞나. "바꾸려면 여기"가 실제 위치인가. **DECISIONS 카드의 "어디"(파일 함수 · configs 키)가 실제로 있는지, 그 configs 키가 정말 동작을 바꾸는지** 본다 — 실행하지 말고 `src/`를 읽어(grep) 그 키가 분기나 계산식에 쓰이는지, 아니면 값을 확인만 하는 이름표인지 본다. **configs 는 건드리지 않는다.** 이름표면 "설정으로 안 됨"으로 고치라고 FAIL 상세에 적는다. 카드 "틀리면"이 코드와 다르면 같이 적는다.
3. **목표대로** — R마다 "확인 방법"대로 새로 실행하면 기대 출력이 나오나. 빈 결과·전부 보류는 FAIL.
4. **데이터를 제대로 읽었나** — 행 수·기간·중복 제거 후 수·제외 행 수가 DATA_CARD와 맞나. 핵심 숫자를 독립 재계산하면 같나(오차 허용은 R의 확인 방법에 적힌 대로, 없으면 정확히).
5. **반론 판정** — 담당자가 할 법한 반대 주장 2개를 만들고("이 건은 빼야 한다", "저 기간은 따로 세야 한다") 조건 C와 데이터만으로 받아들일 수 있는지 판정한다. 받아들이면 핵심 숫자가 얼마로 바뀌는지 적는다. 판정이 갈리면 메인에게 C 행 추가를 권한다.

## report.md 형식 (덮어쓴다. 판정은 세 가지뿐)
```
# verify/report.md — <시각> · 대상 커밋 <해시> · 판정 PASS n / FAIL m / NOT_RUN k
## 사람용 5줄 — 무엇을 어떻게 다시 셌나 / 같았나 / 잡은 것 / 반론 2개와 숫자 / 못 돌린 것
| R | 판정 | 내 재계산 | 결과물 값 | 근거 (명령·파일:줄·행 수) |
| C | 반영 | 어디서 확인 | 문제 |
## 데이터 읽기 대조: 행 수 / 기간 / 고유 수 / 제외 수 — 카드 vs 내가 센 값
## 반론 판정 (2개)
## FAIL 상세: 무엇이 다른가, 어느 숫자가 얼마나 왜곡되나, 메인이 고칠 위치(상자·파일)
```
- **사람용 5줄이 먼저다.** 완전한 문장으로, R·C 번호 대신 말로, 숫자 앞뒤를 띄어 쓴다. 사용자는 이 5줄만 읽는다. 표의 칸은 짧아도 되지만 토큰을 붙여 쓰지 않는다("긴급25·CVD04" 금지 → "긴급 설비 ETCH-25, CVD-04").
- 못 돌린 것은 NOT_RUN으로 솔직하게. 추측으로 PASS를 주지 않는다.
- 산출물(스크린샷·응답 JSON·임시 서버 로그·브라우저 프로필)은 `verify/` 아래에 두되 git에는 report.md 와 own_*.py 만 올라간다(.gitignore 가 처리). 큰 JSON 을 여러 벌 남기지 않는다.
- 보고는 10줄 요약 + 파일 위치. 세부는 파일에.
