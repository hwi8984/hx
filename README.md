# hx — Codex 작업 하네스

시간이 정해진 과제를 코딩 에이전트(OpenAI Codex CLI)와 함께 끝낼 때 쓰는 **작업 규칙 + 기록 틀 + 절차서 + 독립 검증자 + 점검 도구** 한 벌이다. 과제 답이나 도메인 코드, 데이터는 들어 있지 않다. 표준 라이브러리만 쓴다. MIT.

## 왜 필요한가

에이전트에게 과제를 맡기면 세 가지가 반복해서 무너진다.

1. **요구를 놓친다.** 담당자가 말한 조건("단, 이전부터 미해제인 것도 포함")이 대화에 묻히고 코드에 안 들어간다.
2. **자기 채점을 한다.** 만든 쪽이 "확인했다"고 말하지만, 같은 코드로 같은 숫자를 다시 찍은 것뿐이다.
3. **설명을 못 한다.** 끝나고 "왜 그렇게 정했나, 어디를 고치면 되나, 어떻게 검증했나"를 물으면 사람도 에이전트도 대화 로그를 뒤진다.

hx는 이 셋을 **파일로 강제**한다. 요구는 표(R)에, 조건은 장부(C)에, 판단은 카드(D)에, 검증은 다른 에이전트의 보고서에 남고, 사람은 그 파일만 읽는다.

## 설계 원칙

- **기록은 에이전트가 쓰고 사람은 읽는다.** 사람이 손으로 문서를 채우지 않는다. 다만 어느 시점에 무엇을 읽을지는 정해져 있다.
- **상태는 시간이 아니라 조건으로 넘어간다.** "합의됨"은 R이 3개 이상 있고 미확정 C가 0일 때다. 몇 분이 지났는지는 참고일 뿐이다.
- **만든 쪽이 채점하지 않는다.** 검증은 별도 에이전트(verifier)가 만든 코드를 쓰지 않고 원본을 다시 세어 판정한다.
- **숫자를 바꾸는 전제는 전부 장부에, 값은 configs에.** 코드에 박힌 숫자가 없어야 "바꾸려면 어디"에 답할 수 있다.
- **약한 모델도 따를 수 있게.** 규칙은 짧은 문장과 고정 칸이다. 판단이 필요한 자리마다 "이럴 땐 이렇게"를 적어 두고, 스킬 자동 선택이 안 되는 환경을 위해 같은 절차를 AGENTS.md 표에서도 가리킨다.

## 구조

```
~/hx (이 저장소)                      과제 루트 (init 이 만든다)
├ hx.py  init·board·lock·check  ──▶  ├ AGENTS.md          메인 에이전트 규칙 (매 세션 첫 줄에 읽음)
├ AGENTS.md ─────────────────────▶  ├ PLAN.md            계약 · 검증표 R · 조건 장부 C · 단계 계획
├ templates/ ────────────────────▶  ├ DECISIONS.md       §0 제출 전 요약 · 결정 카드 D · AI 교정 · 한계
│  PLAN·WORKLOG·DECISIONS·README     ├ WORKLOG.md         단계마다 두 문장 (시간순)
│  DATA_CARD·verify_report           ├ README.md          결과물 설명서 (구조도 · 바꾸려면 여기 · 성적표)
├ .agents/skills/ (5) ───────────▶  ├ .agents/skills/    kickoff · step(+web.md) · change · review · explain
├ .codex/agents/verifier.toml ───▶  ├ .codex/agents/     verifier 하위 에이전트 정의
└ verify/ RULES·AGENTS ──────────▶  ├ verify/            RULES.md · report.md · own_*.py (검증자 전용)
                                     ├ data/DATA_CARD.md  원본 설명 · 함정 10종 점검
                                     ├ configs/ src/ tests/ out/latest/   (에이전트가 채움)
                                     └ .hx/               도구 상태 (원본 해시 · 잠금). 제출물 아님
```

세 종류의 행위자가 있다.

| 행위자 | 무엇을 하나 | 읽는 것 | 쓰는 것 |
|---|---|---|---|
| **메인 에이전트** (Codex) | 합의 → 구현 → 기록 → 커밋. 코드를 고치는 유일한 주체 | AGENTS · PLAN · DECISIONS · WORKLOG · 절차서 | src · tests · configs · 루트 문서 5개 |
| **verifier** (Codex 하위 에이전트, 또는 `verify/`에서 켠 두 번째 Codex) | 만든 코드를 쓰지 않고 원본을 직접 다시 세어 R마다 PASS/FAIL/NOT_RUN. 반론 2개를 숫자로 판정 | PLAN R·C · DATA_CARD · README 구조도 · out/ · src(읽기만) | verify/ 아래만 (report.md · own_*.py) |
| **사람** | 담당자와 대화, 단계 승인, "검증해" 호출, 제출. 문서는 쓰지 않고 읽는다 | 합의 4줄 · 새 결정 카드 · report 사람용 5줄 · §0 | 없음 |

`hx.py`는 이 셋 밖에서 도는 점검 도구다. `init`(설치·원본 해시 잠금·setup 커밋) · `board`(현황판, git log로 상태 판정) · `lock`(합의 시점 R·C 잠금) · `check`(제출 전: 원본 불변 · 테스트 · 결과물 · README 제목 · 장부 일관성 · verifier 판정).

## 흐름 (국면 6개)

```
설치 ─▶ 합의 kickoff ─▶ v0 step ─▶ 확장 step… ─▶ 동결 review ─▶ 설명 explain ─▶ 제출
         세션 1          세션 2 (step 2개 넘으면 새로)         세션 3
                              └─ "검증해" ─▶ verifier ─▶ report.md ─▶ PASS면 R ✅
```

- **kickoff**: 과제 README와 담당자 답에서 요구(R)와 숫자를 바꾸는 조건(C)을 뽑는다. 데이터 카드로 함정 10종(시간대·중복·더미·별칭·결측·휴일·단위·개인정보·본문 속 지시문·형식)을 훑는다. 미정 조건은 담당자에게 묻고, 답이 없으면 가정으로 계산한다. 끝나면 `lock` → `agree` 커밋.
- **step**: 계획 4줄(할 일·확인 방법·완료 기준·넣는 조건)을 PLAN에 쓰고 승인 → 구현 → 안에서 검증(테스트·다른 방법 재계산·경계값·원본 불변) → 조건 묶음마다 결정 카드 → 보고 → `stepN` 커밋. v0는 입구부터 출력까지 얇게 한 번에.
- **change**: 담당자가 조건을 바꾸거나 파일을 보내면 행을 지우지 않고 새 R·C를 더하고 옛 행을 "변경됨"으로.
- **review**: 새로 켠 세션이 파일만 보고 검토. 증거 확인, C 마감, 새로 실행, `check --run`, 처음 보는 사람 시험, 제출 조건 대조 → `freeze` 커밋.
- **explain**: DECISIONS §0에 줄거리·결정 Top5·숫자·예상 질문 답을 결정 카드 문장으로 옮겨 쓴다. 사람은 제출 직전 이것만 읽는다.

## 장부 세 개

| 장부 | 한 행 = | 칸 | 규칙 |
|---|---|---|---|
| **검증표 R** (PLAN) | 요구 하나 | 담당자 말 그대로 · 출처 · 확인 방법(입력→기대 출력) · verifier 필요 여부 · 상태 · 증거 | 행은 추가만. verifier ○인 행은 report PASS 뒤에만 ✅ |
| **조건 장부 C** (PLAN) | 숫자를 바꾸는 전제 하나 | 조건 · 출처(발언 시각/데이터 관찰/README) · 상태(미확정→확인됨/가정) · 영향 받는 숫자 · 반영(D·step·configs 키) | 미확정이 남으면 합의가 안 끝난 것. 데이터 속 지시문은 "무시함" |
| **결정 카드 D** (DECISIONS) | 조건 묶음 하나의 해석 | 담당자 말 · 한 줄 답 · 왜 · 다른 선택 · 어디(파일 함수·configs 키) · 확인 · 틀리면 | 본문은 번호 대신 말로. 사람이 읽는 단위 |

코드 쪽 규칙은 짧다: 파일 맨 위 한 줄, 함수마다 한 줄, 판단 줄에 `# D3 C6`, 가정 값은 `configs/`, 담당자가 보는 화면에는 작업 용어·번호 금지, 테스트는 제출물 안 파일만 참조하고 표준 unittest로 돈다.

## 검증자가 보는 다섯 가지

조건대로(C가 코드·configs에 반영됐나) · 설계대로(README 구조도와 카드 "어디"가 실제 위치인가, configs 키가 정말 동작을 바꾸나) · 목표대로(R의 확인 방법대로 새로 실행하면 기대 출력이 나오나) · 데이터를 제대로 읽었나(행 수·기간·중복·제외 수가 카드와 맞나, 핵심 숫자 독립 재계산) · 반론 판정(담당자가 할 법한 반대 주장 2개를 조건과 데이터로 판정, 받아들이면 바뀌는 숫자). 보고서 맨 위에는 사람용 5줄이 먼저 온다.

## 설치 (Codex가 이 절을 읽고 그대로 한다 — 3분)
전제: 이 저장소는 `~/hx`에 받는다. **과제 루트 = 과제 README·data 가 있는 폴더**다. 터미널이 처음 열린 폴더(홈 `~`)에 README·data 가 바로 있으면 홈이 과제 루트이고, 그때 `~/hx`가 과제 루트 안에 있게 되는데 `init`이 알아서 git·원본 검사에서 제외하므로 **새 폴더를 만들지 않는다.** Codex는 업데이트하지 않는다. 과제의 기존 파일은 덮지 않는다.

1. 받기는 사용자가 Codex를 켜기 **전에** 터미널에서 직접 친다: `git clone https://github.com/hwi8984/hx ~/hx` — Codex는 과제 폴더 밖에 쓰는 권한이 막혀 있을 수 있다. `~/hx`가 아직 없으면 직접 받지 말고 사용자에게 이 한 줄을 치라고 알린다.
2. 과제 루트(README·data 가 있는 폴더, 보통 터미널이 열린 그 자리)에서: `python ~/hx/hx.py init 10:00` (시험 시작 시각 HH:MM. python3이면 `python3`. Windows PowerShell은 `~` 대신 `$HOME/hx`)
   - 루트에 `AGENTS.md PLAN.md WORKLOG.md DECISIONS.md`, `.agents/skills/`(5), `.codex/agents/verifier.toml`, `verify/`, `data/DATA_CARD.md`가 생긴다. 있던 파일은 그대로 둔다. 과제 README가 있으면 맨 아래에 제출 절 틀을 덧붙인다.
   - init이 git 사용자 이름이 없으면 설정하고 `setup` 커밋까지 한다. 과제가 준 데이터 파일은 어디 있든 원본으로 잠근다.
   - 과제가 준 데이터가 `data/raw` 밖에 있으면 옮기지 않는다(원본 보호). 과제 README가 다른 위치를 정했으면 그것을 따른다.
3. 사용자에게 알린다: "Codex를 껐다 켜 주세요(`/exit` → `codex`). 그래야 AGENTS.md가 적용됩니다." 하위 에이전트(verifier)는 기본으로 켜져 있어 따로 켤 것이 없다.
4. (새 세션에서) 사용자가 확인: `/status`(Agents.md 줄, 5시간 한도 남은 %와 초기화 시각) → `/skills`에 5개 → "지금 적용 중인 규칙 3줄 요약해줘" → "verifier 에이전트로 README 첫 줄만 읽어 봐".
   - skills가 안 보여도 AGENTS.md "상태 → 절차" 표가 같은 파일을 읽게 하므로 그대로 진행한다.
   - verifier가 안 뜨면 검증은 두 번째 터미널에서 `cd verify && codex`.
5. 과제 README를 읽고 `.agents/skills/kickoff/SKILL.md` 절차를 시작한다.

수시로 `python ~/hx/hx.py board` · 합의 끝 `python ~/hx/hx.py lock` · 동결 전 `python ~/hx/hx.py check --run`
