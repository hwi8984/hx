# step — 구현 단계 (한 단계 = R 하나 또는 구조도 상자 하나)

세션 2 첫 진입: PLAN 단계 목록을 읽고 "구현 단계 목록(5~8개, 각각 어느 R)"을 제안해 승인받는다. 아직 만들지 않는다.

## ① 계획 3줄 (+ 건드리는 C) → 승인
할 일 / 확인 방법(무엇을 어떻게 재는가) / 완료 기준(관찰 가능한 결과) / 건드리는 C 번호.
승인 전엔 코드를 고치지 않는다. 승인 뒤 ②~④는 중간 승인 없이 간다.
**v0는** 입구부터 출력까지 모든 상자를 얇게, 실제 데이터로 숫자(웹이면 화면)가 나오는 것이 완료 기준. 가정 C는 가정값으로 계산하고 결과에 `가정: C번호 (확인 필요)` 표시.

## ② 만들기
- 파일 맨 위 한국어 한 줄 "이 파일이 하는 일". 함수마다 무엇·왜 한 줄. 판단 줄에 `# D3 C6`.
- 가정 C의 값·기준·경계·시간대는 `configs/`로 뺀다. 장부 C의 "반영" 칸에 configs 키를 적는다.
- 요청에 없는 기능은 만들지 않는다. 새 문서·새 폴더는 먼저 묻는다.

## ③ 검증 (건너뛰지 않는다)
1. 이 단계의 완료 기준을 재는 테스트 **최소 1개** 실행. 검사 0건·전부 skip·빈 결과는 실패.
2. 핵심 숫자 하나를 **다른 방법**으로 재계산(`verify/own_*.py` 짧은 스크립트, 또는 손으로 센 3건).
3. 건드린 C마다 경계값 1개 확인(기간 경계, 빈 입력, 중복).
4. `data/raw` 불변 확인.

## ④ 기록
- WORKLOG: `## stepN · 시각` 아래 문장 두 개(무엇을 해서 어떤 숫자 / 어떻게 확인) + `(D번호 · )`. 해석을 정했으면 DECISIONS 결정 카드(C 번호 참조).
- 검증표 R 상태·증거 갱신. verifier 칸 ○인 R은 ⏳로 두고 "검증해"를 기다린다(PASS 뒤 ✅).
- 조건 장부 C "반영" 칸(D·step·configs) 채움.
- PLAN 현황판 "다음:" 줄 갱신.
- v0 뒤에는 README "구조도"를 텍스트 그림으로 그리고, 구조가 바뀌는 단계마다 갱신.

## ⑤ 보고 4줄
무엇을 했다 / 왜 / 어떻게 확인했다(명령·결과) / 틀리면 어떤 숫자가 어떻게 왜곡된다(장부 C의 "영향" 칸에서).
코드 용어 대신 구조도 상자 번호. 새 카드 전문. v0 뒤에는 "구조 5문장 설명" + "지금 검증해 달라고 하세요".
45분마다 또는 단계 3개마다 "결정 요약 3줄".

## ⑥ 커밋
`stepN: 무엇 | verify: 결과`. 번호는 git log에 이어서. 검증이 안 됐으면 커밋하지 않고 보고한다.
