# step — 구현 단계 (한 단계 = 실제 코드 변경 하나. 코드 변경이 없는 단계는 만들지 않는다)

세션 2 첫 진입: PLAN 단계 목록을 읽고 "구현 단계 목록(각각 어느 R·C)"을 제안해 승인받는다. 단계 수는 필요한 만큼이다(보통 3~5개). 아직 만들지 않는다.

## ① 계획 블록을 **PLAN.md 단계 절에 쓴다** → 승인
PLAN 의 `### stepN — 이름 (R번호 · C번호)` 블록에 할 일 / 확인 방법 / 완료 기준 / 넣는 조건(이 단계가 적용하는 C) 네 줄을 채우고, 채팅에는 "PLAN stepN 블록을 써 두었습니다. 승인하시면 시작합니다"와 같은 네 줄을 보여 준다. 채팅에만 쓰고 끝내지 않는다.
승인 전엔 코드를 고치지 않는다. 승인 뒤 ②~④는 중간 승인 없이 간다.
**v0는** 입구부터 출력까지 모든 상자를 얇게, 실제 데이터로 숫자(웹이면 화면)가 나오는 것이 완료 기준. 가정 C는 가정값으로 계산하고 결과에 `가정: (내용) (확인 필요)` 표시 — 화면에는 C 번호를 쓰지 않는다.

## ② 만들기
- 파일 맨 위 한국어 한 줄 "이 파일이 하는 일". 함수마다 무엇·왜 한 줄. 판단 줄에 `# D3 C6`.
- 가정 C의 값·기준·경계·시간대는 `configs/`로 뺀다. 장부 C의 "반영" 칸에 configs 키를 적는다. 코드가 확인만 하고 분기하지 않는 값(이름표)은 configs 에 두지 않거나 "설정으로 안 됨"이라고 적는다.
- 담당자가 보는 화면·결과 파일의 문구는 담당자 말로만 쓴다. R·C·D 번호, "하네스", "verifier" 같은 작업 용어는 넣지 않는다.
- 요청에 없는 기능은 만들지 않는다. 새 문서·새 폴더는 먼저 묻는다.

## ③ 검증 (건너뛰지 않는다)
1. 이 단계의 완료 기준을 재는 테스트 **최소 1개** 실행. 검사 0건·전부 skip·빈 결과는 실패.
   테스트는 제출물 안의 파일(`data/` `configs/` `src/`)만 참조한다. 연습 도구·바깥 폴더의 파일을 읽지 않는다. 경로는 `Path` 로 만들고 문자열로 비교하지 않는다(리눅스·Windows 어디서든 통과해야 한다).
2. 핵심 숫자 하나를 **다른 방법**으로 재계산(`verify/own_*.py` 짧은 스크립트, 또는 손으로 센 3건).
3. 건드린 C마다 경계값 1개 확인(기간 경계, 빈 입력, 중복).
4. `data/raw` 불변 확인.
5. 웹이면: HTTP 응답 검사는 표준 라이브러리로. 브라우저 자동 검사(node·Chrome)는 **있을 때만** 쓰고, 없으면 사용자에게 미리보기로 직접 눌러 보라고 안내한다. 테스트가 node·Chrome 없이도 통과해야 한다.

## ④ 기록
- **DECISIONS 결정 카드 — 이 단계가 넣은 조건 묶음마다 하나.** 담당자 말(원문) / 한 줄 답 / 왜 / 다른 선택 / 어디(파일 함수 · configs 키) / 확인(숫자) / 틀리면. 본문은 번호 대신 말로, 번호는 제목 괄호에만. 숫자 앞뒤 띄어쓰기.
- WORKLOG: `## stepN · 시각` 아래 문장 두 개(무엇을 해서 어떤 숫자 / 어떻게 확인) + `(D번호 · )`.
- 검증표 R 상태·증거 갱신. 증거 칸은 `커밋 · verifier PASS · 증거 파일명`만 — 숫자 설명은 카드에. verifier 칸 ○인 R은 ⏳로 두고 "검증해"를 기다린다(PASS 뒤 ✅).
- 조건 장부 C "반영" 칸(D·step·configs) 채움. PLAN 현황판 "다음:" 줄 갱신.
- v0 뒤에는 README "구조도"를 텍스트 그림으로 그리고(상자마다 파일·함수 이름), "바꾸려면 여기" 표에 담당자가 바꿀 법한 것(예: 기준값·정렬 규칙·기간·새 입력 파일·표시 항목 — **과제에 있는 것만**)을 미리 채운다. 구조가 바뀌는 단계마다 갱신.
- README "확인 방법" 성적표 4줄(테스트 수 · verifier PASS · 재계산 차이 · 원본 불변)을 현재 값으로 갱신.

## ⑤ 보고 5줄 (4줄 + 읽을 것)
무엇을 했다 / 왜 / 어떻게 확인했다(명령·결과) / 틀리면 어떤 숫자가 어떻게 왜곡되나.
코드 용어 대신 구조도 상자 번호. 새 카드 전문. 마지막 줄: `읽을 것: DECISIONS D번 카드 (1분)`.
v0 뒤에는 "구조 5문장 설명" + "지금 검증해 달라고 하세요".
45분마다 또는 단계 3개마다 "결정 요약 3줄".

## ⑥ 커밋 → (조건부) 새 세션
`stepN: 무엇 | verify: 결과`. 번호는 git log에 이어서. 검증이 안 됐으면 커밋하지 않고 보고한다.
이 세션에서 끝낸 step 이 2개를 넘었거나 응답이 눈에 띄게 느려졌으면 사용자에게: "step 커밋이 찍혔습니다. 이 세션이 길어졌으니 `/exit` → `codex` 로 새로 켜 주세요. 새 세션은 PLAN·DECISIONS·WORKLOG 를 읽고 이어 갑니다." (긴 세션 하나가 사용량 한도의 대부분을 먹는다.) 아니면 이어서 다음 단계 계획을 낸다.
